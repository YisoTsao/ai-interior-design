# ADR-016 牆體開口改用解析式幾何（偏離 ADR-003 的 three-bvh-csg）
狀態：接受
日期：2026-09-30
背景：ADR-003 / 03 §4 規定開口用 three-bvh-csg 做減法。

> 更正紀錄：初版把「切到 3D 時主執行緒卡住 ~50 秒」歸因於 CSG。後來查明主因是**本機環境**：Node 為 x86 版、跑在 Rosetta，
> Playwright 因此以 x86_64 啟動 Chrome，JIT 程式碼需經 Rosetta 轉譯；改用原生 arm64 Chrome 後，同一場景 3D 首次載入由 36 s 降為 2.2 s
> （見 PROGRESS「決策與偏離」與 `tools/chrome-arm64.sh`）。因此「CSG 造成卡頓」不是本 ADR 的理由。

決策仍維持採用解析式生成（`packages/viewer-3d/src/walls3d.ts`），理由如下：
1. **v1 規格只有「直線牆＋矩形開口」**：這個情況可以精確分解成四邊形，不需要通用布林運算。
2. **可預期與可測**：輸出的三角形數量、A/B/CAP 群組、UV 都是確定的；單元測試驗證「側面面積＝牆面−開口」、「開口處沒有三角形」、「法線方向」。CSG 的輸出是帶細碎三角形的非索引幾何，還要逐三角形重新分類 A/B 面。
3. **成本**：解析式 O(開口數)，同一台機器上每面牆約 1 ms（暖機後）；CSG 每個開口需建兩棵 BVH 並切割三角形（Node 下單一開口約 50 ms）。
4. **少兩個依賴**：移除 `three-bvh-csg`、`three-mesh-bvh`。

作法：
- 平面輪廓仍由 core-geometry 的 `wallQuad`（斜接）提供，viewer 不自行拼牆（B3.1 不變）。
- 側面 A/B 依開口邊界切成垂直帶，開口所在帶只輸出開口上、下方的四邊形；另輸出開口內側面（門框/窗框洞）、頂面（剖面）、端面。
- UV 以 mm 為單位（貼圖 repeat = 1 / 真實尺寸，FR-303 不變）。

後果：
- 好：幾何可單元測試、效能穩定、依賴更少。
- 壞/風險：拱形/斜向開口需另寫 ADR（可只在該類開口使用 CSG）。開口若落在斜接三角區內，洞口可能與端面相交，列為已知限制。
