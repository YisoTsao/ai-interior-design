# ADR-016 牆體開口改用解析式幾何（偏離 ADR-003 的 three-bvh-csg）
狀態：接受
日期：2026-09-30
背景：ADR-003 / 03 §4 規定開口用 three-bvh-csg 做減法。P2 實作後，在 headless Chrome 以範例場景（6 面牆、5 個開口）切到 3D 時主執行緒被佔用數十秒；CPU profile 前段由 three-bvh-csg 的三角形切割/BVH/raycast 佔據。
後續量測顯示 CSG 並非唯一原因（移除 CSG 後仍慢，見 PROGRESS「阻礙」），但 CSG 本身仍有兩個結構性問題：
1. 成本隨三角形與開口數非線性成長，且對共面/細長三角形敏感；
2. 結果為非索引、帶細碎三角形的幾何，後續 A/B 面分組需逐三角形分類。

決策：v1 牆體一律是「直線牆＋矩形開口」，因此改用解析式生成（`packages/viewer-3d/src/walls3d.ts`）：
- 平面輪廓仍由 core-geometry 的 `wallQuad`（斜接）提供，viewer 不自行拼牆（B3.1 不變）。
- 側面 A/B 依開口邊界切成垂直帶，開口所在帶只輸出開口上、下方的四邊形；另輸出開口內側面（門框/窗框洞）、頂面（剖面）、端面。
- 直接產生 A/B/CAP 群組與以 mm 為單位的 UV（貼圖 repeat = 1 / 真實尺寸，FR-303 不變）。
- 時間複雜度 O(開口數)；單元測試：100 面牆 × 3 開口 < 500 ms，並驗證側面面積 = 牆面 − 開口、開口處無三角形覆蓋。

選項與取捨：
- 保留 CSG：通用（可處理斜牆、弧形開口），但慢且不穩定。
- 解析式：只支援矩形開口（v1 規格本來就只有矩形門窗），快、可測、無額外依賴。

後果：
- 好：移除 `three-bvh-csg` 與 `three-mesh-bvh` 依賴；幾何可預期、可單元測試。
- 壞/風險：未來若需要拱形/斜向開口，需另寫 ADR（可只在該類開口使用 CSG）。
- 開口靠近斜接端點且落在斜接三角區內時，側面帶會被夾在 [uStart, uEnd] 內，洞口可能與端面相交；v1 以 validateScene 限制開口在牆長內，實務上影響小，列為已知限制。
